# MCP 2026-07-28 stateless wire behavior (P1-02)

Source: official spec pages `/specification/2026-07-28/basic/transports` and `.../transports/streamable-http` (fetched 2026-10-31). Quotes paraphrased; MUST/SHOULD levels as stated there.

**Streamable HTTP**
- Single MCP endpoint supporting POST. Every JSON-RPC message from the client is its own POST; body is exactly one request or notification (clients MUST NOT send JSON-RPC responses).
- `Accept` MUST list both `application/json` and `text/event-stream`. Server answers a request with one JSON object or a request-scoped SSE stream; notifications get `202 Accepted`.
- No protocol-level sessions; no GET stream; no `Last-Event-ID` resumption. Long-lived change notifications come from a `subscriptions/listen` request. Server→client needs (sampling/elicitation/roots) arrive as `InputRequiredResult` (MRTR, SEP-2322), not server-initiated requests.
- Closing the SSE response stream = cancellation of that request.
- Servers MUST validate `Origin`; if present and invalid → `403`.

**Required request headers (on every POST)**
| Header | Value / rule |
|---|---|
| `MCP-Protocol-Version` | e.g. `2026-07-28`; MUST match body `_meta["io.modelcontextprotocol/protocolVersion"]` |
| `Mcp-Method` | JSON-RPC `method`; all requests |
| `Mcp-Name` | `params.name` or `params.uri` for `tools/call`, `resources/read`, `prompts/get` |
| `Mcp-Param-{Name}` | only for tool params annotated `x-mcp-header`; values non-ASCII/whitespace-padded/sentinel-lookalike must be sent as `=?base64?<b64>?=` |

Body `_meta` carries `io.modelcontextprotocol/protocolVersion`, `.../clientInfo`, `.../clientCapabilities` on every request. **The body is the source of truth.**

**Validation**: header/body mismatch, missing required header, or invalid characters → `400` + JSON-RPC error `-32020` `HeaderMismatch`. Unsupported version → `400` `UnsupportedProtocolVersionError`. Unknown method → `404` + `-32601`. Intermediaries enforcing policy on mirrored headers SHOULD reject requests whose version predates header–body validation.

**Security implication for MCPHorizon (design input, not a verified result):** adapters must derive the logical operation and target from the *body*, then compare with headers; a gateway keyed only on `Mcp-Method`/`Mcp-Name` can be bypassed by a mismatching client if some hop doesn't validate.

**Compatibility**: clients detect legacy servers by trying a modern request first; a `400` with a recognized modern error means a modern server (don't fall back); otherwise fall back to `initialize`. Modern servers answering legacy traffic: GET/DELETE → `405`; ignore `Mcp-Session-Id` and `Last-Event-ID`.
