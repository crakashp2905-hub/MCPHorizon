## Same-OS-user bypass (hardens ENG-PR05)
`sinkproc`: the sink runs as its own uid owning a 0700 data dir; it serves only a configured gateway uid (SO_PEERCRED). Tested as real uids: an agent uid gets PermissionError on direct write/list/journal tamper; via socket it is refused (PEER_NOT_GATEWAY); root with the wrong uid is refused; gateway writes succeed, traversal/symlink/directory blocked.
Limits: root-only tests (skipped without root); Linux only; does not defend against kernel/sandbox escape or an agent holding the gateway uid; the gateway-side permit verification is not yet wired to this sink process; no network/HTTPS path.

## Addendum: intermittent CI failure root-caused (permit fuzzer `sig_flip`)
`token.sig_flip` was generated by rewriting the LAST TWO characters of the token to "AA".  An Ed25519 signature is 64 bytes =
86 base64url chars; the final char carries 2 data bits and 4 padding bits that `effect.b64d` ignores, so that rewrite left the
signature unchanged about 1 time in 256 (token nonces differ per run).  The verifier then correctly accepted an unchanged
signature and the test reported a false "accepted" (seen in CI as `Lists differ: ['token.sig_flip'] != []` and as the bare
`AssertionError` in `scripts/novel_mutants.py`'s baseline run).  Fix: `permitfuzz.flip_sig` changes one character well inside the
signature; regression test checks 300 tokens always change and are rejected; mutant added.
Negative finding (NOT fixed here): `b64d` accepts non-canonical base64url (16 spellings of one signature).  Replay protection is
keyed on the signed nonce, not the token string, so this is encoding malleability, not a forgery; any component that keys state on
the raw token string would be affected.  Tracked as an A01-03 (canonical encoding) item.
