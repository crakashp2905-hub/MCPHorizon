
## N28 — K1: gateway now runs on EffectKernel (CANDIDATE)
The MCP gateway write path uses `EffectKernel.prepare/execute_v1`; the issuer (`require_v1`) refuses effects without a bound CanonicalEffectV1; receipts are signed by a separate "enforcer" identity and carry `witness_kind`. ## N29 — K2: confined runner and sink anchor (CANDIDATE)
`horizon/runtime/runner.py` runs an agent under the enforced sandbox policy by default and REFUSES weaker policies (`POLICY_TOO_WEAK`); the agent edits a private workspace copy and changes are only reported. 14 bypass probes (tcp/udp/raw/unix sockets, writes/reads outside the workspace, symlink/hardlink escape, exec variants, mount, setuid) are all blocked confined and reachable unconfined (control). `FileSink` now records (count, head) after every append, so tail truncation is detected without a caller-supplied anchor.
Limits, stated plainly: proven only on THIS kernel as root in a cloud container — NOT on the owner's designated Linux host (BLOCKED until they supply it); the runner is not yet the mandatory start path for every agent; the anchor sits beside the journal by default so an attacker who rewrites both (or restores both) is not detected (test documents it); ProcessIssuer failure stays fail-closed with no auto-restart because a respawned issuer would mint a different key; no mutation testing was run on K2; running the unconfined control `mount` probe as real root would shadow the host /proc, so it is skipped when unconfined (this crashed the sandbox twice before the fix). Nothing here is independently verified.

## N30 — K3: coding-agent workflow (CANDIDATE, scripted agents)
`horizon/product/codingagent.py`: confined runner -> reported changes -> Gateway/EffectKernel (signed receipts) -> trusted tests. Scripted attacker completes the legitimate task (tests fail->pass) while `.env`/`.github/workflows`/hidden-file writes are refused, the host receiver gets 0 bytes, and nothing lands outside the repo; an unconfined control run exfiltrates the canary and writes outside, so the confinement is what stops it. Report: docs/evidence/product/K3_REPORT.md.
Limits: NO model was run — the "agents" are scripted, so this shows the pipeline permits safe continuation, not that a real agent behaves this way (the earlier live 0/24 result is unchanged until a real model is run); exec/syscall attempts are known only from the agent's own log (advisory) — kernel audit is UNKNOWN; only the one local receiver is observed; deletions are reported NOT_APPLIED (gateway is write-only); the repo is a small toy, same kernel/root caveats as K2.

## N31 — K4: Spectra → Forge → install → Zero on the live environment (CANDIDATE)
`horizon/product/loopb.py`: Spectra runs one probe per effect path through the real runner and asks host-side witnesses (receiver, directory/tree observers) what happened; Forge proposes least-privilege controls + gateway path globs and an independent checker re-derives them (catches missing control, too-broad/hidden glob, utility-floor violation, undeclared unimplementable need); the installer role measures/signs the controls, issues an installation claim and wires the attestation gate into the kernel; Zero returns CONTRADICTED / SUPPORTED_BY_PROBES / UNKNOWN. Drift in a control file turns positive verdicts to UNKNOWN and the gate denies commits. Report: docs/evidence/product/LOOP_B_REPORT.md.
Limits: Spectra's "paths" are a fixed set of five edges and four probes — it does not discover unknown paths; exec is only inferred from a marker and stays UNKNOWN for absence; no observer exists for other destinations (net_other UNKNOWN); SUPPORTED_BY_PROBES is NOT safety; Forge's "synthesis" is a deterministic mapping from reachable edges to runner controls (the runner already requires the full set), so its added value here is the path-glob list, the checker and the explicit unimplementable-needs list, not search; no real HTTPS receiver or independent reviewer; installer/issuer keys are in-process test keys (custody is the owner's decision); no mutation run on K4; same single-kernel caveats.
